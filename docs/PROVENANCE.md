# Provenance — ISO 10383 MIC Registry

What this registry contains, where it comes from, how it is refreshed,
and what is intentionally not covered.

## Source of truth

**One source:** the SWIFT-published ISO 10383 MIC file, hosted at
`https://www.iso20022.org/market-identifier-codes`.

No third-party MIC lists, no `iso20022.org` mirrors, no Wikipedia, no
aggregators. The published file is the only authority. If a value cannot
be traced to it, the field stays null.

## File format consumed

- UTF-8 CSV, LF line endings
- 17 columns, all header names ALL CAPS, all values quoted
- Every field is quoted with `"` — fields containing commas exist in
  `MARKET NAME-INSTITUTION DESCRIPTION`, `LEGAL ENTITY NAME`, and
  `COMMENTS`. `cut -d,` and `awk -F,` corrupt these rows; the parser
  uses Python's `csv` module.
- Dates are `YYYYMMDD`, converted to ISO 8601 on output
- Snapshot date is the download date; the file does not embed one

See `docs/source_format.md` for the verbatim column list and the value
sets observed on 2026-09-23.

## Refresh cadence

SWIFT publishes the MIC file on the **second Monday of each month**.
Modifications become effective on the fourth Monday.

CI fails if `meta.source_snapshot` is more than **60 days old**
(`tools/check_snapshot_freshness.py`). Sixty days is one full missed
cycle — a signal that the update process broke, not that the source is
late.

The refresh process:

1. On or after the second Monday, run `python3 tools/fetch_swift_mic.py
   --download --force --strict`.
2. Inspect the diff between the previous and new `iso10383.json`:
   new MICs, expired MICs, changed names, changed country codes,
   removed MICs.
3. Commit the update as a single PR.
4. Tag a patch or minor release per `CHANGELOG.md`.

A refresh with `REMOVED > 0` is a hard failure (D10). The PR is not
merged until a human confirms the removal was intentional.

## Audit procedure

Every `iso10383.json` carries `meta.source_hash`, a `sha256:` digest of
the raw file the JSON was derived from. Six months from now, if someone
asks "did the October refresh actually run?", the hash answers it.

To verify a JSON against a raw file:

    python3 -c "
    import hashlib, json
    from pathlib import Path
    d = json.load(open('iso10383.json'))
    h = 'sha256:' + hashlib.sha256(Path('raw/MIC_YYYYMMDD.csv').read_bytes()).hexdigest()
    print('match' if h == d['meta']['source_hash'] else 'MISMATCH')
    "

Two runs on the same raw file produce byte-identical JSON. Verified by
`diff /tmp/a.json /tmp/b.json` in `tools/fetch_swift_mic.py` smoke tests.

## Known gaps

- **8 three-level parent chains.** `XEAS -> XEQT -> XBER`, `ICAT ->
  ICAH -> ...`, and six others. The schema models a parent MIC of any
  type; the chains resolve to an operating MIC. Depth is not capped in
  the JSON, but the fetcher refuses chains deeper than 8 levels.
- **`MIC_TYPE` mapping.** The source uses `OPRT` and `SGMT`. The
  registry uses `OPERATING` and `SEGMENT`. The mapping is closed; a new
  value raises at parse time.
- **`STATUS` mapping.** The source uses `ACTIVE`, `UPDATED`, `EXPIRED`.
  The mapping is closed; a new value raises.
- **`MARKET CATEGORY CODE`.** The Release 2.0 factsheet defines 16
  codes. The 2026-09-23 snapshot uses 14 (`ARMS` and `CTPS` are absent).
  The registry's enum is the union of all 16, so a future assignment
  does not require a code change. See D4.
- **No operating hours.** Out of scope (D11). Sourced better from the
  Exchange Calendar registry.
- **No MIC-to-LEI mapping.** Out of scope (D11). The `lei` field on
  each entry is present but unused by any current consumer.
- **No MIC-to-BIC mapping.** Out of scope (D11).
- **Exchange Calendar gap.** Three MICs referenced by the Exchange Calendar registry are not present in the 2026-09-23 ISO 10383 file: `XBEK` (Beirut), `XNBO` (Nairobi), `XQSE` (Qatar). Either they were removed from the source, or Exchange Calendar should drop them. CI reports this as a warning (D6: advisory in v1.0.0, blocking in v1.0.1).
- **No trading currency per MIC.** Derived from `country_code` →
  ISO 4217, not stored.

## Cross-registry snapshots

`tools/iso3166_snapshot.json` and `tools/exchange_calendar_snapshot.json`
are committed snapshots used by the validator for cross-reference
checks. They are regenerated by scripts, committed, and CI-verified.

- `country_code` values validate against ISO 3166 alpha-2.
- Every MIC referenced in Exchange Calendar must exist in `iso10383.json`
  (advisory in v1.0.0, blocking in v1.0.1).

No runtime dependency on either repository. The snapshots are the
interface.

## Versioning

`VERSION` is the single source of truth. `CHANGELOG.md` top heading,
README badge, `iso10383.json` → `meta.version`, and the Parquet footer
(when it exists) must all match. CI enforces this.
