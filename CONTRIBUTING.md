# Contributing to ISO 10383

The registry is a small codebase with a strict discipline. Every rule
in this document exists because it was violated once and cost time.
The rules are not preferences.

Read this file before opening your first pull request. Skim the four
rules and the source discipline if nothing else.

## The four rules

These rules exist because each one cost ISO 3166 time. They are not
suggestions.

### 1. No heredocs for patch scripts

Write `/tmp/script.py`, run it standalone, check its exit code.
Never inline Python with quotes or braces in a heredoc.

**Why:** heredocs have silently corrupted files four times across
the sibling registries. Bash interprets `!` as history expansion,
`$` as a variable, and backslash sequences as escapes — all before
Python sees the content. A script that writes a script fails in a
way that is invisible until you diff the output.

**Correct:**

```bash
cat > /tmp/patch.py <<'PYEOF'
# write this carefully, no shell metacharacters
PYEOF
python3 /tmp/patch.py
```

**Wrong:**

```bash
python3 -c "..."           # quotes and braces get mangled
cat <<EOF | python3        # EOF is not quoted; $VAR expands
```

### 2. `set -euo pipefail` at the top of every shell script

A failed anchor must halt the script. Without this, patch scripts
abort and the shell continues.

**Why:** nine failures in a single release cycle of ISO 3166 came
from a script whose `sed` anchor did not match. The script printed
"done" and left the file half-edited. `set -e` would have stopped at
the first non-match.

**Correct:**

```bash
#!/usr/bin/env bash
set -euo pipefail
```

Applies to `scripts/release.sh`, `tools/check_cross_language.sh`,
and any one-off script in `/tmp` that makes more than one change.

### 3. Adversarial tests on `/tmp` copies, never on the working tree

Copy the file, mutate the copy, verify the mutation. The working
tree is not a test fixture.

**Why:** a patch script that runs against the working tree has no
undo. A patch script that runs against `/tmp/file.py` can be re-run
after a fix because the working tree was never touched.

**Correct:**

```bash
cp tools/validate.py /tmp/test_validate.py
python3 /tmp/patch.py /tmp/test_validate.py
diff -u tools/validate.py /tmp/test_validate.py
# read the diff, then apply
python3 /tmp/patch.py tools/validate.py
```

### 4. File-first

Write a script to a file, run the file, read the output. Never
execute critical logic inline.

**Why:** a script that lives in a file can be re-read, re-run, and
diffed. A script that was typed into `python3 -c` is gone the moment
it exits. When it produces the wrong result, the only option is to
type it again — with the same mistake.

## Source discipline

**Accepted source:** SWIFT's published ISO 10383 MIC file, and only
that file, hosted at:

```
https://www.iso20022.org/market-identifier-codes
```

**Excluded:** third-party MIC lists, mirrors, Wikipedia, aggregators,
blog posts, commercial data vendors.

If a value cannot be traced to the published file, the field stays
`null`. A `null` is honest. An inferred value is a silent bug that
will surface in a downstream consumer's order routing.

### Snapshots

Every cross-referenced value validates against a committed snapshot:

- `tools/iso3166_snapshot.json` — country codes
- `tools/exchange_calendar_snapshot.json` — MICs referenced by
  Exchange Calendar

Snapshots are regenerated by scripts, committed, and CI-verified. No
runtime dependency on either sibling repository.

### Hand-edits rejected

Every change to `iso10383.json` goes through a tool. The tool sets
`meta.updated`, records the source, and writes deterministically.

A hand-edit to `iso10383.json` will fail `tools/export_*.py --check`
on the next run. The fix is to update the source file and regenerate,
or to open an ADR if the source is wrong.

### Deterministic writes

Every generated file is written with:

```python
json.dumps(data, indent=2, sort_keys=True, ensure_ascii=False)
```

LF line endings. Trailing newline. Two runs on the same input
produce byte-identical output.

Python 3.11 and 3.12 produce byte-different output without
`sort_keys=True`. This is why the kwarg is not optional.

## Getting started

```bash
git clone https://github.com/slimissa/iso10383.git
cd iso10383

python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
pip install -e wrappers/python

# Run every gate
python3 tools/validate.py
python3 -m pytest tests/ -q
bash tools/check_cross_language.sh
```

Expected on a clean checkout:

```
OK (with warnings): 2883 MICs validated
...
66 passed
...
OK: 5 suite(s) passed, all wrappers agree
```

The one warning — `3 MIC(s) referenced by Exchange Calendar not in
registry: XBEK, XNBO, XQSE` — is documented and expected. See
`docs/PROVENANCE.md` § Known cross-registry gap.

Toolchain:

| Tool | Version | Purpose |
|------|---------|---------|
| Python | ≥ 3.9 | Tools, tests, CLI |
| Node | ≥ 18 | JavaScript wrapper |
| Cargo | ≥ 1.70 | Rust wrapper |
| Go | ≥ 1.21 | Go wrapper |
| `pyarrow` | ≥ 14 | Parquet export |
| `jsonschema` | ≥ 4 | Schema validation |

Only Python is required for data changes. Node, Rust, and Go are
required only when touching the corresponding wrapper.

### The five layers

Changes happen at one layer and propagate downward. See
`docs/LAYERS.md` for the full model.

| Layer | Location | Committed |
|-------|----------|-----------|
| 0 — Raw | `raw/MIC_YYYYMMDD.csv` | No |
| 1 — Curated | `iso10383.json` | Yes |
| 2 — Derived | Nine files at repo root | Yes |
| 3 — Bundled | `wrappers/*/.../iso10383.json` | Yes |
| 4 — Cross-referenced | `tools/*_snapshot.json` | Yes |

Never hand-edit a committed artifact. Every file except the docs,
the tools, and the tests is generated.

## How to make a change

Six scenarios. Find the one that matches your change.

### Fix a data error

You found a value in `iso10383.json` that disagrees with the SWIFT
file.

**Do not edit `iso10383.json`.** It is regenerated on every refresh.

1. Confirm the error in the raw file.

   ```bash
   grep '"THE_MIC"' raw/MIC_YYYYMMDD.csv
   ```

2. If the raw file disagrees with the registry, the parser has a
   bug. Open an issue. Include the row from the raw file, the
   registry entry, and the field that differs.

3. If the raw file agrees with the registry, the registry is
   faithfully representing the source. The error is at SWIFT. Open
   an issue with the source row and the expected value. The
   maintainers will raise it with SWIFT or note it in
   `docs/PROVENANCE.md` § Known gaps.

**No pull request fixes a data value directly.** A PR that changes
`iso10383.json` and nothing else will fail CI.

### Add a new MIC

MICs come from the source. You do not add them.

A new MIC appears in the registry on the next monthly refresh, when
SWIFT publishes it. If the MIC is missing from the current snapshot
and you believe it should be present, open an issue with:

- The MIC.
- The expected `market_name`, `mic_type`, `operating_mic`,
  `country_code`, and `market_category`.
- The SWIFT publication in which it first appeared.

### Add a field

New fields are rare. The registry's schema is deliberately narrow.
See D11 in `docs/decisions/v1.0.0-decisions.md` for the list of
fields that are explicitly out of scope.

If you believe a new field is warranted:

1. Open an issue describing the field, its source, its type, and
   its expected frequency of population.
2. If the field is in scope, add it in a PR that touches every layer:

   | Layer | Files |
   |-------|-------|
   | Fetcher | `tools/fetch_swift_mic.py` |
   | Schema | `schema.json` |
   | Column order | `tools/export_columns.py` |
   | SQL | `tools/export_sql.py` |
   | CSV | `tools/export_csv.py` |
   | Parquet | `tools/export_parquet.py` |
   | Tests | `tests/test_iso10383_codes.py`, `tests/test_export_*.py` |
   | Wrapper API | All four wrappers, `tests/cross_language_consistency.json` |
   | Docs | `docs/PROVENANCE.md`, `docs/action_types.md`, README |

3. Regenerate the registry and every artifact.

   ```bash
   python3 tools/fetch_swift_mic.py --raw raw/MIC_YYYYMMDD.csv
   python3 tools/export_sql.py
   python3 tools/export_csv.py
   python3 tools/export_parquet.py
   python3 tools/sync_wrappers.py
   ```

4. Run the full gate.

   ```bash
   python3 tools/validate.py
   python3 -m pytest tests/ -q
   bash tools/check_cross_language.sh
   ```

5. Bump the schema's minor version and add a `CHANGELOG.md` entry.

### Add an export format

Say you want an XML export.

1. Write `tools/export_xml.py`. It reads `iso10383.json`, writes
   `iso10383.xml`, and supports `--check`.
2. Reuse `CSV_COLUMNS` or `SQL_COLUMNS` from
   `tools/export_columns.py`. Add a new tuple only if the shape
   genuinely differs.
3. Write `tests/test_export_xml.py`. Follow the pattern of
   `tests/test_export_csv.py`.
4. Add the artifact to `.gitattributes` if it needs a specific
   line-ending policy.
5. Add one line to the `check-exports` job in
   `.github/workflows/validate.yml`.
6. Document the format in the README's Quick Start if it is a
   first-class consumption path, and in `docs/LAYERS.md` § Layer 2.

The tool is the contract. The artifact is disposable.

### Add a wrapper method

The four wrappers are one API surface. A method added to one is
added to all four.

1. Write the method in Python first. The bugs are always in the
   first one.
2. Add a case to `tests/cross_language_consistency.json`. The case
   is the contract.
3. Port to JavaScript, Rust, and Go, following the existing
   naming conventions:

   | Operation | Python | JavaScript | Rust | Go |
   |-----------|--------|------------|------|-----|
   | Lookup | `by_mic` | `byMic` | `by_mic` | `ByMIC` |
   | Segments | `segments` | `segments` | `segments` | `Segments` |
   | Parent | `operating_mic` | `operatingMic` | `operating_mic` | `OperatingMIC` |

4. Every wrapper's test suite reads the shared fixture. Do not add
   language-specific tests unless the language imposes a constraint
   the fixture cannot express.
5. Bump all four wrapper package versions in one commit (D16).

### Add a test

The test suite has eight files at the root, plus per-wrapper
suites.

| Change | Test file |
|--------|-----------|
| Ground-truth values | `tests/test_iso10383_codes.py` |
| Validator behavior | `tests/test_validate_schema.py` |
| Hierarchy rules | `tests/test_self_reference.py` |
| CSV artifact | `tests/test_export_csv.py` |
| SQL artifact | `tests/test_export_sql.py` |
| Parquet artifact | `tests/test_export_parquet.py` |
| CLI behavior | `tests/test_cli.py` |
| Cross-wrapper consistency | `tests/test_wrappers.py` |

Follow the fixture-anchor rule: no test hardcodes a MIC, a count,
or a country code. Every expected value reads from
`tests/cross_language_consistency.json` or from `iso10383.json`
itself. If the fixture changes, the anchors change with it.

## The monthly refresh

SWIFT publishes on the **second Monday** of each month. The refresh
runs automatically on the 15th. You will almost never do it by hand.

### Cross-registry checks

The validator checks every MIC against the Exchange Calendar
snapshot and every country code against the ISO 3166 snapshot.
Cross-registry checks are blocking by default in v1.0.1. Three
MICs are in the allowlist at
`tools/validate.py::KNOWN_EXCHANGE_CALENDAR_GAPS`:
`XBEK`, `XNBO`, `XQSE`.

Adding a MIC to the allowlist requires an ADR amendment. See
[ADR 0007](./docs/decisions/0007-cross-registry-allowlist.md).
Removing one requires the sibling registry to be updated first.

`python3 tools/validate.py --advisory` reverts to the v1.0.0
behavior: cross-registry gaps become warnings, not errors.

If the automated refresh fails or you need to run it manually:

```bash
python3 tools/fetch_swift_mic.py --download --force --strict

# Compare against the previous snapshot
cp iso10383.json /tmp/old.json
python3 tools/fetch_swift_mic.py --raw raw/MIC_new.csv
python3 tools/refresh_diff.py /tmp/old.json iso10383.json
```

The diff prints four lines:

```
NEW:      3 operating, 1 segment
EXPIRED:  0 of the new entries are already expired
CHANGED:  5 (market_name=3, country_code=2)
REMOVED:  0 (0 operating, 0 segment)
```

### If `REMOVED > 0`

**Stop.** Do not regenerate artifacts. Do not commit.

A removed MIC is the change class most likely to break downstream
consumers. The refresh workflow fails the diff step and requires
human confirmation. D10.

Investigate:

```bash
# Was the MIC renamed?
grep '"THE_MIC"' /tmp/old.json
grep 'THE_MIC' iso10383.json

# Is it in Exchange Calendar?
grep -i 'THE_MIC' docs/exchange_calendar_mics.txt

# Is it in a sibling registry?
grep -i 'THE_MIC' tools/*_snapshot.json
```

If the removal is real — the venue closed — confirm on the venue's
website or in SWIFT's release notes, then regenerate artifacts and
commit with a `CHANGELOG.md` entry explaining the removal. If the
removal is not real — the venue still operates — the source may
have a bug. Do not merge. Open an issue.

### If everything else

```bash
python3 tools/export_sql.py
python3 tools/export_csv.py
python3 tools/export_parquet.py
python3 tools/sync_wrappers.py

python3 tools/validate.py
python3 -m pytest tests/ -q
bash tools/check_cross_language.sh

git add -A
git commit -m "Refresh: ISO 10383 snapshot YYYY-MM-DD

NEW:      N operating, M segment
EXPIRED:  ...
CHANGED:  ...
REMOVED:  0"
```

Tag a patch or minor release per Semantic Versioning. A monthly
refresh that adds MICs is a minor release. A refresh that corrects
a value is a patch.

## Cutting a release

Releases are cut by `scripts/release.sh <version>`. Nothing else.

```bash
# Preview
scripts/release.sh 0.2.0 --dry-run

# Cut
scripts/release.sh 0.2.0
```

The script:

1. Verifies preconditions: clean tree, on `main`, no existing tag,
   `CHANGELOG.md` has a `[<version>]` section.
2. Bumps the eight version sites.
3. Regenerates all nine Layer 2 artifacts and all four Layer 3
   bundles.
4. Runs the full gate: validator, freshness, three export `--check`
   modes, `sync_wrappers --check`, root tests, cross-language.
5. Commits and pushes.
6. Polls CI until the run for the pushed commit is `completed
   success`.
7. Tags with a message derived from the `CHANGELOG.md` section.
8. Creates the GitHub release and verifies the body is not a
   placeholder.
9. Writes `docs/v<version>-verification.md`.

The script refuses on a dirty tree, wrong branch, missing
`CHANGELOG` section, gate failure, or CI failure. A tag on a red
commit is not recoverable without a delete-and-retag cycle, so the
script refuses to create one.

### Preparing a release

1. Move everything under `[Unreleased]` in `CHANGELOG.md` to a new
   `[<version>] - <date>` section.
2. Leave a fresh `[Unreleased]` at the top.
3. Update the compare-link footer.
4. Commit.

   ```bash
   git add CHANGELOG.md
   git commit -m "release: prepare v0.2.0"
   ```

5. Run `scripts/release.sh 0.2.0`.

## Commit conventions

Conventional Commits, loosely. The prefix tells a reader where to
look.

| Prefix | Use for |
|--------|---------|
| `feat:` | A new tool, a new wrapper method, a new export format |
| `fix:` | A bug in a tool, a wrapper, or a generator |
| `data:` | A monthly refresh of `iso10383.json` |
| `docs:` | README, ADRs, CONTRIBUTING, PROVENANCE, LAYERS |
| `test:` | New tests, test refactors |
| `chore:` | Version bumps, dependency updates, CI tweaks |
| `release:` | The release-preparation commit |

The subject line is imperative, lowercase, no trailing period, under
72 characters.

The body, when present, explains why the change was made. The diff
explains what changed. A commit that adds a field should say which
ADR or issue motivated it.

### Commit message examples

```
fix: reference operating MIC before declaring it missing

The fetch of 2026-09-23 raised on `XEAS -> XEQT` because `XEQT`
is a segment, not an operating MIC. The parser assumed every
`operating_mic` value pointed to an operating MIC. It does not.

The parser now resolves the full parent chain and records
unresolvable chains in `meta.broken_chains`. See ADR 0002.

data: refresh ISO 10383 snapshot 2026-10-15

NEW:      2 operating, 0 segment
EXPIRED:  0 of the new entries are already expired
CHANGED:  1 (market_name)
REMOVED:  0 (0 operating, 0 segment)
```

## Pull request process

1. **Open an issue first** for anything beyond a typo or a
   documentation fix. The maintainers will confirm the change is in
   scope before you invest time.

2. **Fork and branch.** Branch from `main`. Name the branch for the
   change: `fix/xeas-chain`, `feat/expired-since-flag`.

3. **Make the change.** Follow the four rules. Follow the source
   discipline. Regenerate every artifact the change touches.

4. **Run the local gate.**

   ```bash
   python3 tools/validate.py
   python3 -m pytest tests/ -q
   bash tools/check_cross_language.sh
   python3 tools/check_version_consistency.py
   python3 tools/export_csv.py --check
   python3 tools/export_sql.py --check
   python3 tools/export_parquet.py --check
   python3 tools/sync_wrappers.py --check
   ```

   Every command must exit 0 (the validator may exit 0 with warnings
   — that is expected).

5. **Open the PR.** The description should name the issue, explain
   the change, and include the output of the gate commands.

6. **CI runs five jobs.** See `.github/workflows/validate.yml`:

   | Job | Purpose |
   |-----|---------|
   | `validate-json` | Validator, version consistency, freshness, root tests |
   | `check-exports` | Three export `--check` modes plus `sync_wrappers --check` |
   | `check-cli` | CLI smoke test and CLI tests |
   | `check-wrappers` | Four-language matrix |
   | `check-cross-language` | Shared fixture across all four wrappers |

   A red CI is a signal, not an obstacle. Read the failing job's log
   and fix the underlying issue. Do not push a second commit that
   only disables the check.

7. **Wait for review.** The maintainers review for source discipline,
   determinism, and cross-layer consistency. A PR that adds a field
   to `iso10383.json` without regenerating the artifacts will be
   sent back. A PR that changes a wrapper method without updating
   the shared fixture will be sent back.

8. **Squash merge.** Every PR lands as one commit on `main`. The
   squash commit message is the PR title.

## Reporting a bug

Open an issue. Include:

- What you did.
- What happened.
- What you expected.
- The output of `python3 tools/validate.py`.
- The output of `python3 -m pytest tests/ -q`.
- The version of the registry you are using (`meta.version` from
  `iso10383.json`).

If the bug is a data error — a MIC with the wrong name, a
mis-typed market category, a missing MIC — include:

- The MIC.
- The wrong value.
- The expected value.
- The source: the row in the SWIFT file, or a link to a public
  announcement, or the SWIFT release note that documents the
  correction.

**Do not open a pull request that edits `iso10383.json` directly.**
Data errors are fixed at the source, or documented as known gaps.

## Security disclosure

Do not open a public issue for a security vulnerability.

Use GitHub's private vulnerability reporting at:

```
https://github.com/slimissa/iso10383/security/advisories/new
```

The registry has a small attack surface — it is a data file and a
set of readers — but three areas warrant care:

- **The downloader.** `tools/fetch_swift_mic.py` fetches a URL. A
  compromised DNS or an unvalidated redirect could serve a
  different file. The parser's invariants (MIC patterns, closed
  enums, parent-chain resolution) are the defense. Report any
  bypass.
- **The CLI.** `tools/iso10383_cli.py` reads a file path from
  `--registry` and from the `ISO10383_REGISTRY` environment
  variable. Report any path-traversal or command-injection issue.
- **The wrappers.** Each wrapper reads a bundled JSON file. Report
  any issue where a caller-supplied path or object can cause the
  wrapper to read a file it should not, or to return data from a
  different registry.

The maintainers will acknowledge within 72 hours and provide a
remediation timeline.

## A short note on what "done" means

A change is done when:

1. The source of truth is updated. For a data change, that is the
   raw file. For a code change, that is the tool.
2. Every generated artifact is regenerated.
3. Every `--check` mode passes.
4. The root test suite passes.
5. All four wrapper suites pass.
6. `tools/check_cross_language.sh` reports `OK`.
7. The commit message explains why.

A change that touches one layer and not the ones below it is not
done. The nine artifacts at repo root are the contract with
downstream consumers. They are always derived from `iso10383.json`.
Never edit them by hand.
